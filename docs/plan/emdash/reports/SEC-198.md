### Where the SEC-09 CA comes from
`apps/web/scripts/certs/prod-ca-2021.crt` is the public "Supabase Root 2021 CA" (valid until 2031-04-26). Its SHA-256 fingerprint is `80:70:25:AD:50:D4:ED:21:9D:2C:9C:7D:29:9C:00:4F:82:4E:B0:0C:F7:F6:5A:FE:F6:07:D0:7B:72:E6:CA:FA`, and `pg-tls.test.ts` pins it. I verified it in three ways on 2026-11-26:
1. It is byte-identical to Supabase's published `https://supabase-downloads.s3-ap-southeast-1.amazonaws.com/prod/ssl/prod-ca-2021.crt`.
2. `openssl s_client -starttls postgres -verify_hostname` against the production pooler host gives `Verification: OK`, with the chain `*.pooler.supabase.com` <- Intermediate 2021 <- this root.
3. Node `tls.connect` with `pgSslFor()` gives `authorized: true` (handshake only, no credentials sent).

Remote hosts never fall back to `rejectUnauthorized: false`, in the repo scripts, the Docker admin or the backup job. `DATABASE_CA_CERT` (PEM text or a file path, the same rules as INF-9) overrides the CA. `ssl*` URL parameters are stripped.

## Owner-only checklist
1. **Restore drill.** Follow `runbooks/backups.md` §5 after the first backup that uses the new settings, then fill in the drill log.
2. **`BACKUP_AGE_RECIPIENT`.** Set it on the `production` environment (`age-keygen`, public `age1…` line). The backup now fails closed if it is missing or malformed.
3. **Backup role.** Apply `supabase/roles/growgen_backup.sql` to production, set the password with `\password growgen_backup`, then store the URL as `gh secret set BACKUP_DATABASE_URL --env production` (`runbooks/backups.md`). Until then the backup uses the owner URL and logs a warning.
4. **CI role.** Apply `supabase/roles/growgen_ci_readonly.sql`, set the password, and point the `ci-readonly` secret `DATABASE_POOLER_URL` at `growgen_ci_readonly.<ref>`. Then re-run `web-ci` (`runbooks/ci.md` "Read-only CI role").
5. **`EMDASH_TARGET_FINGERPRINT`.** Set it on `production`. The value comes from `emdash migrate --from-config --status` on a trusted machine, after checking the host. `apply_migrations` fails until it is set; that is by design.
6. **Branch protection.** Add a ruleset on `master` and `feat/emdash`: no force pushes or deletions, PRs required, the `web` check required, no bypass. Also give `GITHUB_DISPATCH_TOKEN` an expiry and scope it to this repo only.
7. **Docker admin CA.** Nothing to do: the image ships the committed CA and verifies by default. Rebuild the image to pick it up.
8. **Online admin exposure.** Host it only behind `cloudflared` with no public inbound port, and set `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD`.

## Residual risks
- Supabase may rotate its root CA (this one expires 2031-04-26). The backup's fingerprint check, `pg-tls.test.ts` and the image would then need the new CA committed; connections fail closed until then.
- The Hyperdrive local connection used by `astro build` (wrangler/miniflare) has its own TLS handling, which this story did not change.
- The legacy `e2e.yml` and `sync-content.yml` are not SHA-pinned.
- `growgen_ci_readonly` has no default privileges, so a new collection or derived table needs the role script re-run (otherwise the PR build fails with `permission denied`, or an empty-collection check trips). Until the owner applies it, PR CI still uses the owner URL.
- Backups keep `credentials` (passkey public keys) so the restored admin can be signed into; they are not secrets.
- PR CI can read unpublished and scheduled drafts in `ec_*` and all media metadata (accepted, `runbooks/ci.md`): PR builds run only for this repo's branches, are never deployed, and the role cannot write.
- Both `options` allow-lists fail closed: a new key EmDash starts reading in the build is invisible to CI until added (the build may then render a default), and a new key is not backed up until added.
