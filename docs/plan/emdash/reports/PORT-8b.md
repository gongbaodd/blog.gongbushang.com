### Embed (`apps/web/scripts/derive/`)
- **Merge with MIG-3**: took the branch's `embed.ts`, `Embeddable` type from MIG-3, `table: EmbeddingTable = "post_embeddings"` as 5th parameter passed to `embeddingIndex` / `upsertEmbedding` / `loadEmbeddings`; log wording post/episode kept; header comments merged. `embedPosts(client, episodes, mode, 3, "podcast_embeddings")` works (test: podcast table path, mock client rejects SQL for another table).
- **1 Provider switch**: all rows are stale after a model change; derive re-embeds the whole corpus in one run. `DERIVE_EMBED_MAX` and the parser are removed (ignored with a warning if set). If the run cannot finish (quota, outage, skip, no provider), rows with a matching `content_hash` stay in use for relates/UMAP (`loadEmbeddings(..., acceptOtherModel = true)`, result field `staleModel`, log "kept from a previous model"): the corpus never shrinks because of a switch; only new or edited items are `missing`. Seeds always tag legacy vectors with the LM Studio model id (documented in both seed scripts).
- **2 Same text as legacy**: `\n` becomes a space in both provider paths (`normalizeEmbeddingInput`). `content_hash` is unchanged. Spot check: `pnpm --filter web derive:compare-embeddings -- 20` (`scripts/derive/compare-embeddings.ts`): read-only cosine of cached LM Studio vectors against fresh Workers AI vectors for a sample. **Not run** (needs credentials); the owner runs it. Expect about 0.99+; a median under about 0.95 means do not switch.
- **3 Context 8,192 tokens**: input cap is 6,000 estimated tokens (ASCII 0.3, other code points 1, astral 2; CJK-safe), cut at code point boundaries. A context-length error on a batch falls back to item by item, each cut to 60 % and retried (max 5). Truncated ids are logged (`result.truncated`); documented in the runbook.
- **4 Quota**: 429/5xx after retries, or Workers AI error code 4006, raises `WorkersAiError` and derive treats the rest as missing (warning, build continues, earlier batches are already committed). `DERIVE_EMBED=require` makes it a hard failure. Other errors (401, bad shape) still throw.
- **5 Token and model**: only `CF_AI_TOKEN` / `CLOUDFLARE_AI_API_TOKEN` (a Workers-AI-scoped token); `CLOUDFLARE_API_TOKEN` is never used. `DERIVE_EMBED_MODEL` validated (charset `A-Za-z0-9@._:/-`, no `..`/`//`); account id validated. `runbooks/data.md` gained a Workers AI section; `runbooks/ci.md` lists `CF_AI_TOKEN` + `CF_ACCOUNT_ID` (names only, not wired; workflows belong to Builder-Infra). Test parses a response in the documented envelope (`result.shape`, `result.data`, `success`, `errors`, `messages`); the model page documents `{ shape, data }` and an 8,192-token context.

### Colorize (`apps/colorize/`)
**Not exact. Stopping point for the owner, see options.**

- Replaced the custom MMCQ and the 650-line `png.ts` with node-vibrant's own code: `@vibrant/core` `BasicPipeline` + `@vibrant/quantizer-mmcq` + `@vibrant/generator-default` (registered exactly as `node-vibrant/node`, filter `a >= 125 && not near-white`, colorCount 64), `chroma.deltaE` and the repo's `TITLE_COLOR_MAP` (imported from `packages/consts/colors.ts`), and `fast-png` for decoding. A test compares against the real `Vibrant` on block images (exact), another that every map hex maps to itself.
- Legacy input: full-size original -> `sharp().png()` -> `Vibrant.from(png)`, which scales down to 1/5 (`quality` 5) with Jimp before quantizing. The Worker asks Cloudinary for `f_png,c_scale,w_0.2` (1/5 scale PNG).
- **Acceptance, 100 real Cloudinary covers from local `derived.cover_colors`** (`node apps/colorize/scripts/accept.ts covers.json 100`): `bgColor` equal for **52/100**, `titleColor` equal for **81/100**. Mismatching `bgColor`: median CIEDE2000 2.1, max 35.6, 13 above 5 (a different swatch was picked). Cause: only the down-scale (Cloudinary resampler vs Jimp). Proof: legacy recompute equals the cache 14/14 and the port fed node-vibrant's own Jimp-scaled pixels equals the cache 14/14 (`scripts/diag-legacy.mjs`). Tried other renditions (two-step 0.5 then 0.4, `e_blur:0`, `q_100`, `fl_awebp`): none better (the two-step one was worse).
- **CPU**: not provably within 10 ms. Node, decode + quantize, includes JIT warm-up: median 3.2 ms, p90 10.9 ms; renditions up to 325k pixels (p90 175k). Large covers are likely over 10 ms on a cold Workers Free isolate. `wrangler dev` ran (functional, cache hit/miss, 401), wall times 190 ms to 1.9 s are Cloudinary rendition generation; it does not measure CPU. Bundle: 190.68 KiB, gzip 45.52 KiB. `wrangler tail` procedure for the owner is in `apps/colorize/README.md`.
- Options (not chosen, owner decides): (a) keep derive cache-first and use the Worker only for new covers, accepting about 48 % small bg differences (median CIEDE2000 2) and 19 % different title colours for those; (b) run legacy `getColorSet` in CI/Mac for the few new covers per build (sharp is fine there), drop the Worker; (c) find a Cloudinary rendition that equals Jimp's area-average (none found); (d) port Jimp's resize and decode a larger rendition (needs full-size decode, over 10 ms, would need Workers Paid or a Container).
- Fixes requested: fails closed (`COLORIZE_TOKEN` unset -> 503, tested); allowlist only `res.cloudinary.com/<CLOUDINARY_CLOUD_NAME>/image/upload/` with no redirects; Cache API keyed by the rendition URL (tested hit/miss); README test command corrected (`pnpm --filter colorize test`; the root vitest config does not include `apps/`); devDependencies declared (`vitest`, `wrangler`, `typescript`, `node-vibrant`, `@types/chroma-js`) at the versions the web importer already resolves. The Worker is not wired to overwrite cached colours.
- **Lockfile**: `pnpm install` in a worktree re-resolved unrelated packages (picomatch, sourcemap-codec, tinyglobby), so the lockfile was assembled by hand: only the new `apps/colorize` importer (devDependency versions copied from the web importer) and `fast-png@8.0.0` / `iobuffer@6.0.1` entries; `git diff --stat pnpm-lock.yaml` = 47 insertions, 0 deletions; `pnpm install --frozen-lockfile` passes; root `astro check` 0 errors.
