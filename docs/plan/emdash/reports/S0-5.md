## Approach: media provider (not Storage adapter)
A custom media provider can be registered from our own code. Evidence (emdash 1.6.0 / @emdash-cms/cloudflare 1.6.0):
- `emdash({ mediaProviders: MediaProviderDescriptor[] })` (`config-B27hvMjf.d.mts:2366`); descriptor = `{id, name, icon?, entrypoint, capabilities, config}` (`placeholder-PFMxMYTa.d.mts`).
- `cloudflareImages()` is just a descriptor function whose `entrypoint` is a runtime module exporting `createMediaProvider(config)` (`@emdash-cms/cloudflare/dist/index.mjs`, `media/images-runtime.mjs`). Nothing privileged.
- `virtual-modules` generates `import { createMediaProvider } from "<entrypoint>"` (line 316), so any resolvable path works; we pass an absolute path to `runtime.ts`.
- Provider stores the Cloudinary `public_id` (as `MediaValue.id`) and builds `f_auto,q_auto` URLs; no bytes proxied, no `Storage` needed. `storage` is optional in the config, so R2 is gone entirely. Trade-off: the built-in "local" library tab remains visible but uploads there will fail (no storage); use the Cloudinary tab.

## Implementation (`apps/web/src/lib/cloudinary-media/`)
- `sign.ts`: SHA-1 signing via `crypto.subtle`, multipart upload and destroy request builders, delivery URL builder.
- `provider.ts`: `createCloudinaryProvider(config, getEnv, fetch, now)`: list (Admin API, Basic auth, prefix `growgen/`), get, upload (`/auto/upload`, signed, 10 MB cap, alt stored in `context`), delete (`/image/destroy`, `invalidate`), `getEmbed` (with `getSrc`), `getThumbnailUrl`.
- `runtime.ts`: EmDash entrypoint; reads `CLOUDINARY_CLOUD_NAME/API_KEY/API_SECRET` from `cloudflare:workers` env, falling back to `process.env`. Nothing hardcoded.
- `index.ts`: config-time `cloudinaryMedia({folder})` descriptor.
