# Scout note S0-3: prerendered pages calling EmDash at build time

Checked 2026-11-24. Sources: npm (`emdash` 1.6.0, `@emdash-cms/cloudflare` 1.6.0, `@astrojs/cloudflare` 14.4.9, `wrangler` 4.168.0; repo pins `astro` 7.3.3), docs.emdashcms.com (deployment/cloudflare, deployment/database, deployment/route-caching), docs.astro.build (Cloudflare adapter), and the shipped `dist/` code of the packages above.

**Verdict:** Probably works. No EmDash doc or issue covers prerender/SSG, so the S0-3 spike must prove it. If the spike fails, use the fallback below.

## Need
Public pages with `export const prerender = true` call `getEmDashCollection` / `getEmDashEntry` during `astro build`, on the Cloudflare adapter, with Postgres (Supabase) behind Hyperdrive (D2, D3).

## Use
- **Mechanism 1, request context is optional.** `getRequestContext()` returns `undefined` outside a request. `getEmDashCollection` computes `serveDrafts = ctx?.editMode || ctx?.preview` (query-*.mjs ~L232), so a build serves published content only. No ALS frame is needed.
- **Mechanism 2, DB singleton.** `getDb()` (loader-*.mjs ~L1221) builds a Kysely instance from the virtual config when no request DB is set, so build-time reads don't need a request.
- **Mechanism 3, Hyperdrive reads `env`.** The `hyperdrive()` dialect takes its connection from `env[binding]` (`cloudflare:workers`) and throws `BINDING_NOT_FOUND` if it's missing (`@emdash-cms/cloudflare` db/hyperdrive.mjs).
- **Mechanism 4, adapter prerenders in workerd.** Astro 6+/7 with `@astrojs/cloudflare` prerenders in workerd by default (`prerenderEnvironment: "workerd"`), so `import { env } from "cloudflare:workers"` works at build time. Wrangler reads the Hyperdrive local connection string from `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_<BINDING>` (wrangler 4.168.0 cli.js ~L73008) when the binding is not remote.

Recommended setup for the spike:
```js
// astro.config.mjs (sketch)
export default defineConfig({
  output: "server",
  adapter: cloudflare(),
  integrations: [react(), emdash({ database: hyperdrive({ binding: "HYPERDRIVE" }) })],
});
```
```ts
// src/pages/blog/[slug].astro (sketch)
export const prerender = true;
export async function getStaticPaths() {
  const { entries } = await getEmDashCollection("posts");
  return entries.map((e) => ({ params: { slug: e.data.legacy_slug } }));
}
```
- CI build env (GitHub environment secret, name only): `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE` set to the Supabase **direct or session** string. Builds then skip Hyperdrive.
- Spike check: build 3 posts, grep `dist/` for the body text, count DB round trips, and confirm no drafts appear.

Fallback A (if workerd prerender can't reach the DB): set `prerenderEnvironment: "node"` on the adapter and use `postgres({ connectionString: process.env.DATABASE_URL })` from `emdash/db` for the build. The runtime stays on Hyperdrive. This needs one config that picks the dialect by environment, which the spike must test.

Fallback B (D2's own fallback): SSR plus `cacheCloudflare()` route caching with per-collection tags. EmDash invalidates those tags on publish (deployment/route-caching doc).

Known unknowns: how the request-scoped Hyperdrive pool (hyperdrive.mjs header comment) behaves when one build renders hundreds of pages; build time at N posts.

## Considered and rejected
- **Astro live collections (`emdashLoader`)**: run per request, so they don't prerender. Not for D2.
- **D1/SQLite for the build**: breaks D3 (Postgres everywhere).
- **Node-only build with `postgres()` as the only path**: that is Fallback A, kept as backup, not the default.

## Free-tier impact
- Hyperdrive: a build that uses `localConnectionString` doesn't spend the 100k queries/day Hyperdrive quota.
- Supabase: the nightly and per-publish builds keep the project active, which helps the 7-day pause (INF-6 still applies).
- Workers CPU (10 ms) and subrequest limits don't apply at build time. Script size is unchanged.
