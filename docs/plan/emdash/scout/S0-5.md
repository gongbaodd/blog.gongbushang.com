# Scout note S0-5: Cloudinary as EmDash media storage

Checked 2026-11-24. Sources: npm search (`emdash cloudinary`, `@emdash-cms`, `emdash storage`, `emdash markdown`), GitHub code search in `emdash-cms/emdash`, plugins.emdashcms.com (its search endpoint returns "not enabled", and the registry only lists sandboxed plugins), `emdash` 1.6.0 dist types, Cloudinary docs (authentication signatures, upload API reference, fetch vs auto-upload), and Workers Web Crypto docs.

**Verdict:** No Cloudinary adapter, media provider, or plugin exists. Build a thin `Storage` adapter over Cloudinary's REST upload API (D6 option 2), with `fetch` and Web Crypto SHA-1. Fallback: `r2()` binding plus Cloudinary Auto-Upload mapping. Note that the plan's `s3()` fallback doesn't run on Workers.

## Need
Media files live on Cloudinary, with the `f_auto,q_auto` delivery URLs kept stable (D6, §10). Douban and other hot-linked images get re-hosted during migration.

## Use
**Option 2, thin Storage adapter (recommended).**
- Register it in `emdash({ storage: { entrypoint: "<module>", config: {...} } })`. The module exports `createStorage(config) => Storage` (`CreateStorageFn`). Built-ins use the same shape: `emdash/storage/s3`, `emdash/storage/local`, `@emdash-cms/cloudflare/storage/r2`. Config must be serializable, so read secrets from `env` (`cloudflare:workers`) or `process.env`, never from `astro.config`. The exact `entrypoint` form for a local module is unverified; the spike must check it.
- `Storage` methods (dist `types-*.d.mts`): `upload({key, body, contentType, cacheControl?}) → {key, url, size}`; `download(key, {range?}) → {body, contentType, size, lastModified?}`; `delete(key)` (idempotent); `exists(key)`; `list({prefix, limit, cursor}) → {files, nextCursor?}`; `getSignedUploadUrl(...)`; `getPublicUrl(key): string`; optional `getClientUploadOrigin()`.
- `getSignedUploadUrl` should throw `EmDashStorageError` with code `NOT_SUPPORTED`. The local adapter does the same, and `api/media/upload-url` catches that code (dist L21-23). The admin then uploads through the server, so Cloudinary needs no direct PUT.
- Signed upload (Cloudinary docs): sign every field except `file`, `cloud_name`, `resource_type`, `api_key`, including `timestamp` (Unix seconds). Sort by name and join as `name=value` with `&`. Append the API secret with no separator. SHA-1 hex digest (SHA-256 also accepted). POST multipart to `https://api.cloudinary.com/v1_1/<cloud_name>/image/upload` with `file`, `api_key`, `timestamp`, `signature`, plus the signed fields.
- Workers: `crypto.subtle.digest("SHA-1", bytes)` is supported (Workers Web Crypto table). `fetch` plus `FormData` is enough. No Node SDK.
- Delete: `POST /v1_1/<cloud>/image/destroy` with `public_id` and `timestamp`, signed the same way.
- Remote re-hosting: Cloudinary's `file` parameter accepts a remote http(s) URL. Use `headers` for hotlink-protected hosts. This is the Douban path.
- `getPublicUrl(key)` returns `https://res.cloudinary.com/<cloud>/image/upload/f_auto,q_auto/<key>`, which keeps delivery URLs stable.

**Option 3, fallback (Workers).** `r2({ binding: "MEDIA" })` for storage, plus a custom domain on the R2 bucket and a Cloudinary Auto-Upload mapping on that domain. Cloudinary then pulls originals on first request. Auto-Upload is documented as a separate feature from `fetch` (fetch doc, "Comparing fetch to auto-upload"). The mapping setup is unverified.

**Option 3b, local admin (§10 fallback only).** `s3()` to R2's S3 API works, but EmDash's own docs say `s3()` is Node-only and must not get credentials in `astro.config` on a Worker build. It fits the local-admin fallback, not production.

**Other option to spike.** `mediaProviders` in `emdash()` config (`MediaProviderDescriptor`, `createMediaProvider(config)` with `list/get/upload/delete/getEmbed/getThumbnailUrl`). It can browse Cloudinary assets directly, but its storage model differs from `Storage`. Not chosen.

## Considered and rejected
- **Node `cloudinary` SDK 2.11.0 (npm)**: Node-only. Replaced by signed `fetch`.
- **Registry plugins**: sandboxed only, and D1-only (not Postgres), so they're excluded.
- **`@anantagnanam/emdash-storage*` (0.1.0-rc.1)**: R2 and Google Drive only. Not Cloudinary.
- **`s3()` on Workers**: unsupported by EmDash docs (see above).

## Free-tier impact
- Cloudinary (25 credits per rolling 30 days): uploads use storage and bandwidth credits. Avoid eager transformations. Use `f_auto,q_auto` on delivery only, so derived images are cached. The Douban re-host adds storage on the order of MB.
- R2 fallback (Standard storage, free tier): 10 GB-month storage, 1M Class A and 10M Class B operations per month, free egress.
- Workers: upload bodies are buffered in memory (128 MB limit), so cap file size in the adapter.
