# GON-249 Scout: Markdown editor widget for `body_md`

Checked: 2026-11-27. Installed `emdash` 1.6.0 (apps/admin pins ^1.5.0; lockfile resolves 1.6.0). Paths are relative to the repo root; `E` = `node_modules/.pnpm/emdash@1.6.0_*/node_modules/emdash/dist`, `A` = `node_modules/.pnpm/@emdash-cms+admin@1.6.0_*/node_modules/@emdash-cms/admin/dist`.

## 1. How a plugin supplies a field widget

**Use the `fields` export.** The docs and the installed runtime agree. `fieldWidgets` is metadata, not the render hook.

- Docs: https://docs.emdashcms.com/plugins/creating-native-plugins/react-admin/ (`export const fields = { name: Component }`; props below).
- Type: `PluginAdminExports { widgets?; pages?; fields?: Record<string, JSX.Element> }` in `E/types-YTpIfKXX.d.mts` (search `interface PluginAdminExports`).
- Runtime: `A/App-6p4snG9E.js`, `resolvePluginFieldWidget` reads `pluginAdmins[pluginId]?.fields?.[widgetName]` and needs only a function.
- Props: `value`, `onChange(value)`, `label` (host does not render one), `id` (`field-<slug>`), `required`, `options`, `validation`, `minimal`. Each widget sits in an error boundary.
- Schema opt-in: `widget: "<pluginId>:<name>"` (`E/src/schema/types.ts:344,426`). The registry update path accepts `widget` (`E/src/schema/registry.ts:1585`). `scripts/schema/apply.mjs` never modifies existing fields, so `body_md` needs a one-time PATCH to set the widget. The field type stays `text`, so stored bytes are unchanged.
- `fieldWidgets` exists too: `PluginAdminConfig.fieldWidgets?: FieldWidgetConfig[]` (`E/types-YTpIfKXX.d.mts:1634`), with `FieldWidgetConfig { name, label, fieldTypes, elements? }` (`:1605`). `elements` is for sandboxed Block Kit only. Declare it with `fieldTypes: ["text"]` for listings, but it is not required for a trusted widget. This settles the open point in the research doc.
- Wiring: descriptor in `apps/admin/astro.config.mjs` `plugins: [...]` with `format: "native"`, `adminEntry`, `fieldWidgets` (`E/src/astro/integration/runtime.ts:105-135`). The admin module is statically imported (`E/virtual-modules`, `generateAdminRegistryModule`). Pattern to copy: `apps/admin/src/dashboards/plugin.ts`. Docs also say `admin: { entry }` in `definePlugin`, matching `PluginAdminConfig.entry`.
- Traps: `usePluginField(pluginId, fieldType)` in the admin bundle is keyed by field type and is not used by the field renderer. Do not use it. `MediaPickerModal` is exported by `@emdash-cms/admin` (`A/index.d.ts`, props `open, onOpenChange, onSelect(item: MediaItem)`), not by `emdash/ui` (site-only). apps/admin has no direct dependency on `@emdash-cms/admin`, so add it at exact `1.6.0`. Pin `@codemirror/state` and `@codemirror/view` to the versions already resolved (6.7.6 and 6.43.15) to avoid two state instances.

## 2. Existing packages that could supply the editor

**Nothing suitable found.** No Markdown editor widget exists in EmDash or its registry.

- EmDash admin 1.6.0 ships CodeMirror 6 in `A/CodeEditor-FZqFz0f8.js`, but only for html/css/javascript and it is not exported. Rejected.
- Admin rich text (TipTap) changes the stored format, which breaks byte-identical Markdown. Rejected.
- `@emdash-cms/plugin-field-kit` 0.1.4 (npm, native): widgets for `json` fields only. Rejected on field type.
- `emdash-plugin-puck` 0.3.0 (npm, MIT, markoinla): Puck page-layout widget for `json` fields. Rejected on field type and data model.
- `emdash-emit` 0.2.0 (npm): Markdown and Portable Text sync. Rejected because it changes the storage model (description only, not installed).
- plugins.emdashcms.com (checked 2026-11-27): no Markdown, code or CodeMirror widget in the "recently updated" list. Search covers the rest; it was not exhaustively scanned.
- Build it from `@codemirror/view` 6.44.2, `@codemirror/state` 6.7.6 and `@codemirror/lang-markdown` 6.5.2 (all MIT, npm `time.modified` 2026-08 to 2026-11).

## 3. Can `renderMarkdown` run in the browser?

**Yes, after changes.** `apps/web/src/lib/markdown.ts` is not browser-ready as written.

- `import { bundledLanguages } from "shiki"` loads 346 grammars and 65 themes. Measured with esbuild (browser, minified, scratch only): full set about 1.28 MB gzip. Shiki core plus JS regex engine, github-dark theme and 10 grammars: about 140 KB gzip. Load grammars on demand per fence.
- `@astrojs/markdown-remark` 7.3.1 has a browser build for `#mdx-processor` that throws on MDX. The 3 `.mdx` posts cannot use that path. Either preview them with the md pipeline and flag the difference, or leave MDX preview out.
- `rehype-katex`: `katex.min.js` is about 76 KB gzip, plus `katex.min.css` (24 KB) and fonts. Bundle them through Vite from node_modules. No CDN.
- Mermaid: apps/web pins `^11.15.0` (client script via `astro-mermaid`). In the admin, use lazy `import("mermaid")` with the same version. Measured: about 873 KB gzip if every chunk loads. Per-diagram chunks load only when used.
- PlantUML: `shiki-plantuml` is a highlighting grammar only. apps/web renders no diagrams, so the preview only needs highlighting.
- `rehypeCloudinary` (`apps/web/src/lib/cloudinary.ts`) is pure string code and safe in the browser.
- Refactor: move the remark/rehype plugin list out of `markdown.ts` into a shared module. Add a browser entry that uses `shiki/core`, `shiki/engine/javascript` and on-demand grammars. Add a parity test that renders one fixture through both entries and compares HTML.
- Worker and server impact: none. Preview runs in the browser. The admin is Node in Docker, so the 10 ms CPU limit and the 1 GB RAM budget are not affected.

## Recommendation

1. Native plugin in `apps/admin`: descriptor with `adminEntry` and `fieldWidgets`; admin module exports `fields.markdownEditor` (CodeMirror 6 with `@codemirror/lang-markdown`, split preview from the shared browser renderer, `MediaPickerModal` inserting `![alt](url)`).
2. One-time schema PATCH: `widget: "<pluginId>:markdownEditor"` on `posts.body_md`. Type stays `text`.
3. Spike gates before code merges: byte round trip on all 995 posts (check CRLF, trailing newline, BOM; the admin text input's normalisation was not inspected); preview parity fixture; measured bundle size in the Docker build.

Not verified here: byte-identical round trip through the admin's text input, and the `#mdx-processor` browser path beyond its source.

**Free-tier impact:** none for the editor (client bundle, no CDN). Library inserts reuse existing Cloudinary assets. Any new upload counts against the 25-credit Cloudinary budget. The Cloudinary provider already has `upload: true`.
